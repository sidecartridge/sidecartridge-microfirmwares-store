# Publishing a microfirmware to the store

This repository is the **store**. It does not host anybody's firmware. It keeps a **registry** of
**origins**, where an origin is a creator plus the URL of an `apps.json` that creator hosts
themselves. A build job fetches every origin, merges them into one catalogue per channel, and
publishes it. Booster on the device downloads that catalogue.

So the change a creator makes here is small: one entry in one registry file, pointing at a URL they
control. Because the store stores a pointer rather than a copy, later releases need no further pull
request.

## Before touching anything, establish these

Ask if you do not already know. Do not guess, and do not proceed on a maybe.

1. **The `apps.json` URL**, hosted by them, reachable now. HTTP or HTTPS both work here, because the
   build fetches server-side.
2. **Which channel**: stable, testing or development. Stable unless they say otherwise.
3. **Their creator id**, a lowercase-kebab slug, unique on the platform. It becomes their filter key
   in the store, so it should be one they can live with. Changing it later reads as a different
   creator.
4. **Whether the entry already exists.** Read the registry first. Updating an existing entry and
   adding a new one are different jobs.

Fetch their `apps.json` and read it before editing anything. Two failures are worth catching now
rather than in review:

- `image` and `binary` URLs inside it **must be HTTPS**, even though the catalogue URL itself need
  not be. A browser loads those directly.
- Every app needs `previous_versions`. It may be `[]`, but omitting it is the single most common
  validation failure.

## 1. Pick the registry file

| Channel | File |
| ------- | ---- |
| Stable | `origins/atari-st.json` |
| Testing | `origins/atari-st-test.json` |
| Development | `origins/atari-st-dev.json` |

Atari ST is currently the only platform with a registry. Check `platforms.json` and `origins/` if
that seems to have changed.

**Never edit `atari-st/apps.json` or its `apps-test` / `apps-dev` siblings.** Those are generated by
the build and overwritten on every run. A pull request that changes them gets sent back.

## 2. Append the entry

Add one object to the end of the `origins` array. Mind the comma after the previous entry.

```json
{
  "creator": {
    "id": "retro-homebrew",
    "name": "Retro Homebrew Collective",
    "url": "https://retro-homebrew.example"
  },
  "official": false,
  "enabled": true,
  "url": "https://retro-homebrew.example/atari-st/apps.json"
}
```

- `official` is **always `false`**. `true` marks the first-party SidecarTridge origin, exactly one
  entry per registry may carry it, and a creator entry that sets it is rejected.
- `enabled` is `true`. Setting it `false` keeps the entry on file but leaves it out of the build.
- Use `url`. There is a `source` field for files kept inside this repository; it is not for
  creators.
- `creator` also takes optional `image` and `contact`.

## 3. Validate, using exactly what the gate runs

```bash
pip install jsonschema                              # enables the strict validator
python3 tools/build_catalog.py --check --strict
```

A pass ends with `check: OK`. Anything else is a failure, and the lines above it name the file and
the rule. `--strict` **fetches** the URL, so this also catches an unreachable host or a mistyped
path, which is the failure most likely to embarrass someone in review.

If it fails, read the message and fix the cause. Do not weaken the check, do not skip `--strict`,
and do not edit anything under `schema/` to make an entry pass.

To see the apps rendered in the actual site:

```bash
python3 tools/build_catalog.py --platform atari-st
python3 -m http.server                              # then open http://localhost:8000
```

That prints a line per origin, such as `- retro-homebrew (unofficial): +3 app(s)`.

**These local builds are throwaway.** Never commit the regenerated `atari-st/apps.json`. Revert it
before committing:

```bash
git checkout -- atari-st/
```

## 4. Open the pull request

Commit the registry change **on its own**. The diff should be one file and a handful of lines.

A useful body carries the `apps.json` URL, one line on what the microfirmwares do, and anything a
reviewer should know. Opening the PR triggers the required **Validate origins** check, which
revalidates the entry and refetches the URL. It must be green before the PR can merge.

## What the build does to their data, so nobody is surprised

- Apps are tagged with the creator id and shown under that name.
- **Duplicate `uuid`s resolve in SidecarTridge's favour.** A creator app sharing a `uuid` with
  theirs is dropped. Tell them to use their own ids.
- **Device names are rewritten** to `ST`, `STE`, `MegaST`, `MegaSTE`, `TT`, `Falcon`. Case,
  punctuation and a leading platform name are ignored, so `Atari MegaST` resolves. A name matching
  nothing is kept as written and reported, never discarded, but it appears as its own filter entry.
- **`description` is sanitised** to a whitelist of tags when rendered.
- **A `uuid` listed in `blacklist/<platform>.json` is withheld** from every channel of that
  platform, whoever published it. That file is the maintainers' emergency brake, not something a
  creator edits. Never add or remove an entry there as part of a publishing change.

## Afterwards

No second pull request. To ship a new version they update their own `apps.json` in place at the
same URL, and the store rebuilds daily and picks it up.
